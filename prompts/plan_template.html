List Scheduled TriggersPLAN

Add a read-only CLI view of the triggers already scheduled for a session.

repo · charlie-bot scope · trigger CLI deps · none

1 Problem / Goal

The goal is to make a session's persisted one-shot wake-ups, called scheduled triggers, inspectable before an operator adds another watch. Trigger scheduling and persistence are out of scope.

2 Context

A scheduled trigger resumes a CharlieBot session after a delay or when watched work finishes. Operators can create these triggers, but cannot inspect the triggers already scheduled for the session before adding another watch. Sources: src/cli/main.py:19-25; src/core/triggers.py:322-337

The unified command dispatcher exposes trigger creation as charliebot schedule-trigger. The component responsible for trigger lifecycle, TriggerManager, persists each record as a JSON file under the session's triggers directory; no read-only CLI path currently loads those records for inspection. Sources: src/cli/main.py:19-25; src/core/triggers.py:322-337, 677-687

3 High Level Solution

Add a read-only charliebot triggers list command that resolves the current session, loads its trigger records through the existing manager, and formats them for inspection. Trigger files remain the single source of truth; the command owns no state.

sessions/{id}/triggers/*.json→ triggers list→ one row per trigger

4 Detailed Design

4.1Schemaprecision-read layer

charliebot triggers list is read-only, resolves the session from the current working directory, and exits 0 after printing a table or no triggers.

ColumnContent
idTrigger id (the JSON file stem).
statepending / fired / expired.
watchWatch targets, or - for a pure delay.
fires-inTime remaining until --max-wait elapses.
messageThe wake-up message.

Boundaries: the persisted trigger JSON format is unchanged. A malformed record surfaces the loader error instead of being skipped.

4.2Design Detailsoptional-read layer

  • CLI integration: register triggers list in the unified command map and reuse cwd-based session resolution.
  • Read path: ask TriggerManager for records, derive display-only fields, then render aligned plain-text columns.
  • Verification: cover populated, empty, and malformed-record cases with command-level tests, then run the existing CLI suite.

5 Trade-offs

1 Scope: list triggers for the current session only, or across all sessions?

Recommendation: current session only, keeping the command's scope explicit.

Tradeoff: consistent with the rest of the CLI, but triggers created from other sessions stay invisible.

Full story, no prior knowledge required — expand to check the recommendation by hand
  • Session here names the working directory's persisted trigger collection: every charliebot schedule-trigger run on that directory writes its record there, and triggers list would read only that collection.
  • Cross-session visibility inherits whatever the CLI's other read commands do, so changing scope to "all sessions" reaches triggers the current directory did not write.
  • Worked example: a directory holds two published triggers; a third session elsewhere holds one. Current-session scope shows those two only, cross-session shows all three.
  • Each row's existence is anchored to its JSON file, so the rendered list is checkable against what was persisted Sources: src/core/triggers.py:322-337, 677-687.

2 Which trigger states should the command display?

Resolved: all persisted states.
