1 Where your model is right, and where it stopsaffirm

Binning solves a real problem. The glow renderer builds a compiled shader per shape profile and caches by that profile's length. Every frame's radius differs, so unbinned radii would force a fresh compile each step; the sixteen bins cap the shader-side cache. That is the design's whole job, and it lives shader-side.

Where the model stops: the step "each dimension now has at most sixteen values, so the variant total is small" holds only while the cache key is one dimension. The frame cache key is not one dimension, so the inference breaks. Source: ~/workspace/photonfarm/shader_cache.py

2 The missing mechanism: the frame cache keys on the joint state, not the binmechanism

The frame cache checks raw values, not bins. The sixteen bins protect only the shader cache, which sits later in the chain. Two steps show why.

The compiler records a guard for each raw value a frame touches

When the compiler builds one frame, it records every int, shape, and branch result it touches as a guard. The next call re-checks each guard against the raw values that step actually carried. If any guard fails, the whole frame recompiles.

The bin comes after the frame guard, so the guard sees the raw radius

The check happens before binning. It compares not "is the bin the same" but "is the raw value still in the recorded band".

The real code, its place in the chain, and a hand-checkable case:

# ~/workspace/photonfarm/shade_ops.py, the binner the reader names
_BINS = (16, 32, 64, 128, 256, 512, 1024, 2048, 4096, 8192, 16384,
         32768, 65536, 131072, 262144, 524288)   # sixteen bins

def bin_radius(r: int) -> int:
    """Round the radius up to the nearest bin boundary."""
    for b in _BINS:
        if r <= b:
            return b
    return _BINS[-1]

# call site, inside the glow pass
S_bucket = bin_radius(max_radius)   # returns a python constant
# S_bucket enters the shader cache key

For a hand check, max_radius = 300 maps to S_bucket = 512; max_radius = 400 maps to the same shader bin, while a changed row count can still fail the frame guard before the bin is used.

Binning sits after the frame guard and before the shader: it protects the shader cache, not the frame cache.

3 Worked example: frames 41 and 42 from one rampworked example

Both frames fall in the same radius bin. Only their guards decide what each frame does.

End to end: frame 42 recompiles although its bin did not change

Frame 41 packs 14 rows with max_radius 300, which rounds up to bin 512. It compiles once, and its guards record row-count = 14 and the radius band 257 to 512.

Frame 42 packs 17 rows with max_radius 301. Its bin is still 512, so the shader cache hits. The row-count guard fails, because 17 is not 14, so the whole frame recompiles.

Source: ~/workspace/photonfarm/logs/ramp_frames_41_42.log

Contrast: the same bin, and no recompile

Frame 42 again, but with 14 rows and max_radius 301. Its bin is 512 and its radius is inside the recorded band, so every guard holds. The frame cache hits and nothing recompiles.

The only change from the end-to-end case is the row count. A changed row count alone is enough to break a guard.

Source: ~/workspace/photonfarm/logs/ramp_frames_41_42.log

4 Recomposing the reader's arithmeticreconcile

The "sixteen variants" account holds under a one-dimensional key. Frame 42 shows the second key at work: its row count, not its bin, forced the recompile. Fact Under the joint key, the three guarded quantities multiply: 4 row counts × 7 radius bands × 3 offset groups = 84 frame variants, each paid with a full frame recompile. The run logged about 76 recompile frames per node across the ramp, about 29 minutes of serial compilation per node, which is where "68% of the stall" lives. Source: ramp guard log, four nodes

The sixteen bins cap the shader-side variant count; the frame-side variant count is set by the guard product and the frame cache limit, and the two caps do not bound each other.
