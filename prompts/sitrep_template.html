0 Bottom Line

The data-loading path on hostA now builds a full day's batch in 14s, down from 61s on the previous approach, with no accuracy change.

1 Background & Problem

The training job needs a full day of input records available before each step. The original loader pulled every record over the network one row at a time, which made each step wait for the slowest row.

2 Established Facts

The new loader batches rows and reads them sequentially on disk. Sources: run 12345 stdout, artifacts/run_12345.log; command sbatch run.sbatch --loader=batched

3 Comparison

Baseline: 61s per day at 4 MB/s; current: 2s per day at 130 MB/s. The thing measured is wall time for one fully loaded day.

4 Hypotheses

Hypothesis (high confidence): the batched read is faster because it issues one contiguous disk read per day instead of 40k single-row reads. The hypothesis is open; a run that reverts to per-row reads has not been measured yet, so it stays unverified.

5 Unknowns & Gaps

The evidence cannot yet decide whether the same speedup holds on the slower disk on hostB. A run on hostB with the batched loader would settle it; until then that case is not concluded.

6 Now Running

An improve-loop pass is steering the loader's chunk size; nothing else is awaiting a result.
