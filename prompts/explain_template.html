1 Where your model is right, and where it stopsaffirm

Binning solves a real problem. The glow renderer builds a compiled shader per shape profile and caches by that profile's length. Every frame's radius differs, so unbinned radii would force a fresh compile each step; the sixteen bins cap the shader-side cache. That is the design's whole job, and it lives shader-side.

Where the model stops: the step "each dimension now has at most sixteen values, so the variant total is small" holds only while the cache key is one dimension. The frame cache key is not one dimension, so the inference breaks. Source: ~/workspace/photonfarm/shader_cache.py

2 The missing mechanism: the frame cache keys on the joint state, not the binmechanism

When the compiler builds one frame, it records every int, shape, and branch result it touched as a guard. The next call re-checks each guard against the raw values that step actually carried; if any guard fails, the whole frame recompiles. The check happens before binning, so it compares not "is the bin the same" but "is the raw value still in the recorded band".

The real code, its place in the chain, and a hand-checkable case:

# ~/workspace/photonfarm/shade_ops.py:141-155, the binner the reader names
_BINS = (16, 32, 64, 128, 256, 512, 1024, 2048, 4096, 8192, 16384,
         32768, 65536, 131072, 262144, 524288)   # sixteen bins

def bin_radius(r: int) -> int:
    """Round the radius up to the nearest bin boundary."""
    for b in _BINS:
        if r <= b:
            return b
    return _BINS[-1]

# call site :204-205, inside the glow pass
S_bucket = bin_radius(max_radius)   # returns a python constant
# S_bucket enters the shader cache key

For a hand check, max_radius = 300 maps to S_bucket = 512; max_radius = 400 maps to the same shader bin, while a changed row count can still fail the frame guard before the bin is used.

packer emits max_radius→frame entry: dynamo checks guards (raw value)→block forward (compiled frame)→glow pass bins the radius→shader cache (16 bins)→kernel

Binning sits after the frame guard and before the shader: it protects the shader cache, not the frame cache.

4 Recomposing the reader's arithmeticreconcile

The "sixteen variants" account holds under a one-dimensional key; under the joint key the first three quantities alone are 4 × 7 × 3 = 84 slots, each paid with a full frame recompile. Fact The farm's run confirms it: ~76 recompile frames per node across the ramp, about 29 minutes of serial compilation per node, which is where "68% of the stall" lives.

The sixteen bins cap the shader-side variant count; the frame-side variant count is set by the guard product and the frame cache limit, and the two caps do not bound each other.
