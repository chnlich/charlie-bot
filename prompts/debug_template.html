2 How does this normally work?

Four pieces make up the picture. Artists save frames to the primary store, whose files carry mtimes in the primary's clock. A fetcher on the render node pulls every 60 seconds and copies a frame when its primary mtime is newer than the cache copy's stamp. Cached copies are stamped with the render node's own clock at copy time. The review wall serves straight from the cache and never touches the primary.

3 Why did it happen?

The render node's clock ran four minutes fast, so every cache stamp ran four minutes ahead of the primary's timeline. The fetcher's update rule compares a source mtime against that forward stamp, so a re-export made less than about four minutes after the previous sync of the same frame compares as not newer and is skipped. The skip repeats on every later pull, because the comparison and both of its inputs stay unchanged: the frame sticks until an edit's primary mtime passes the stamp. Skews this size are invisible on their own clocks, so nothing surfaced until the wall disagreed with what artists had just saved.

Worked example, hand-checkable with four timestamps (frame 041): v1 saved 09:37:10 (primary mtime). Next pull at 09:38:00 copies v1; the render node clock at that instant reads 09:42:00, so the cache copy carries stamp 09:42:00. v2 saved 09:41:00 (primary mtime). Next pull at 09:42:00 compares source mtime 09:41:00 against cache stamp 09:42:00: 09:41:00 < 09:42:00, so "not newer," and v2 is skipped. Every later pull repeats the same comparison against the same stamp, and the stuck window equals the skew at copy time: four minutes here. Sources: ~/workspace/reviewwall/fetch.log, ~/workspace/reviewwall/replay_041.log.
